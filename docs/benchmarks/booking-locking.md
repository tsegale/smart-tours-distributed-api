# Seat reservation under contention: pessimistic vs optimistic vs atomic

Generated by `benchmarks/run_booking_contention.py --runs 3` on 2026-10-29 09:45 UTC.
Measured, not estimated: 3 run(s) per strategy, strategy order rotated each round. Re-run the
script to reproduce.

## Scenario

- One departure with **500 seats**. **100 virtual users** share **1000 booking attempts** (k6 `shared-iterations`), 1 seat each, so it sells out half way through.
- Every request goes client -> api-gateway (JWT check) -> booking-service -> PostgreSQL, on the compose
  network. One JWT per VU from `scripts/dev_token.py`, a unique `Idempotency-Key` per attempt.
- `PAYMENT_PROVIDER=fake`: the hold and the payment row are written, but no network call to a PSP is made.
- Before each measured run, a warm-up run of 200 attempts on a separate departure (not reported).
- booking-service as in `docker-compose.yml`: 4 uvicorn workers, SQLAlchemy pool 5 + 10 overflow per worker,
  `lock_timeout` 5 s, optimistic strategy 8 attempts with full-jitter backoff (5 ms base, 100 ms cap).
